**02  /  ANTES DE ABRIR CLAUDE CODE**

**NO CONSTRUYAS TODAVÍA**

La velocidad de Claude Code solo sirve cuando la dirección es correcta.

Hay un error que veo constantemente cuando alguien empieza a implementar IA.

| EL ORDEN EQUIVOCADO Encuentra una herramienta ↓ Piensa en un agente ↓ Abre Claude ↓ Empieza a construir | LAS PREGUNTAS QUE LLEGAN TARDE ¿Para quién es esto? ↓ ¿Qué problema resolvemos? ↓ ¿Cómo funciona hoy? ↓ ¿Qué resultado queremos mejorar? ↓ ¿Qué datos tenemos? ↓ ¿Cómo sabremos si funciona? |
| ----- | ----- |

En una empresa, construir es solo una parte de la implementación. Antes necesitas entender el problema, el proceso, los usuarios, los datos, las restricciones, los riesgos y el resultado esperado.

| PRINCIPIO OPERATIVO LA REGLA — Problema antes que herramienta. — Diagnóstico antes que arquitectura. — Requerimientos antes que desarrollo. — Validación antes que implementación. |
| :---- |

**Claude Code puede ayudarte a ejecutar más rápido. Pero velocidad sin dirección solo significa llegar antes al lugar equivocado.**

**03  /  CAMBIO DE MENTALIDAD**

**DE “CONSTRUIR IA” A IMPLEMENTAR IA**

Una demo y una implementación no demuestran lo mismo.

| EL ENFOQUE IMPROVISADO Herramienta ↓ Demo ↓ Agente ↓ Automatización ↓ Buscar dónde utilizarla Empiezas desde la tecnología y esperas encontrar después un problema suficientemente importante. | EL ENFOQUE PROFESIONAL Problema ↓ Proceso ↓ Impacto ↓ Diagnóstico ↓ Requerimientos ↓ Diseño ↓ Validación ↓ Implementación ↓ Adopción ↓ Mejora Empiezas desde una necesidad real y utilizas tecnología únicamente cuando existe una razón para hacerlo. |
| ----- | ----- |

| DIFERENCIA CRÍTICA UNA DEMO DEMUESTRA QUE ALGO PUEDE FUNCIONAR. Una implementación demuestra que puede generar valor dentro de una organización. No es lo mismo. |
| :---- |

**05  /  MÉTODO CAIO · ETAPA 1**

**01\. IDENTIFICAR EL PROBLEMA**

¿Qué está saliendo mal, costando demasiado o limitando el resultado?

Antes de pensar en IA necesitamos entender qué merece nuestra atención. Detectar una molestia no es suficiente: hay que conectar la fricción con impacto real.

| SEÑALES Trabajo manual ↓ Tiempos altos ↓ Errores repetitivos ↓ Retrabajo ↓ Información dispersa ↓ Decisiones lentas ↓ Cuellos de botella ↓ Poca trazabilidad ↓ Pérdida de conocimiento ↓ Dificultad para escalar | LO QUE NECESITAMOS MEDIR Frecuencia ↓ Volumen ↓ Impacto ↓ Costo ↓ Personas afectadas ↓ Consecuencia operacional ↓ Consecuencia económica ↓ Riesgo ↓ Urgencia |
| ----- | ----- |

| GATE DE VALOR NO TODO LO QUE PUEDE AUTOMATIZARSE DEBE AUTOMATIZARSE. La pregunta no es “¿Podemos usar IA aquí?”. La pregunta es “¿Existe suficiente valor como para justificar resolver esto?”. |
| :---- |

| OUTPUT · PROBLEM STATEMENT Actualmente \[USUARIO / ÁREA\] tiene dificultad para \[PROCESO / TAREA\] debido a \[CAUSA / RESTRICCIÓN\], generando \[IMPACTO\]. Queremos mejorar \[RESULTADO\] de \[BASELINE\] a \[OBJETIVO\]. |
| :---- |

**06  /  MÉTODO CAIO · ETAPA 2**

**02\. DIAGNOSTICAR**

¿Qué está ocurriendo realmente?

Aquí dejamos de asumir. Mapeamos cómo funciona el proceso actualmente y buscamos entender qué hay detrás del problema.

**—** Inicio del proceso y trigger.

**—** Pasos y responsables.

**—** Sistemas utilizados.

**—** Entradas y salidas.

**—** Decisiones, reglas y excepciones.

**—** Datos y aprobaciones.

**—** Tiempos, errores y retrabajos.

**—** Dependencias y puntos de fricción.

| DISCIPLINA DIAGNÓSTICO ≠ ENTREVISTA SUPERFICIAL No buscamos únicamente saber qué quiere el cliente. Buscamos comprender suficientemente bien su operación como para distinguir entre síntoma y causa; deseo y requerimiento; idea y problema real. |
| :---- |

| OUTPUT · DIAGNÓSTICO CAIO Un mapa estructurado del problema, el proceso AS-IS, los stakeholders, los datos, las fricciones, los riesgos, los supuestos y la información que todavía falta. |
| :---- |

**07  /  MÉTODO CAIO · ETAPA 3**

**03\. DISEÑAR LA SOLUCIÓN**

¿Cuál es la forma más simple y segura de producir el resultado?

**Después del diagnóstico podemos empezar a pensar en solución. No antes.**

| DECISIONES DE DISEÑO Qué cambia en el proceso ↓ Qué tareas hará IA ↓ Qué seguirá haciendo una persona ↓ Dónde habrá revisión humana ↓ Qué datos entran y salen ↓ Qué sistemas se conectan ↓ Qué decisiones puede tomar ↓ Qué decisiones no debe tomar ↓ Qué ocurre ante un error | COMPONENTES POSIBLES Reglas tradicionales ↓ Automatización ↓ Software existente ↓ APIs ↓ Bases de datos ↓ Modelos de IA ↓ RAG ↓ Agentes ↓ Revisión humana |
| ----- | ----- |

| PRINCIPIO DE ARQUITECTURA IA NO ES LA SOLUCIÓN. IA es uno de los componentes posibles de la solución. |
| :---- |

| OUTPUT · DISEÑO CONCEPTUAL Flujo TO-BE, responsabilidades humanas y automáticas, datos, sistemas, controles y restricciones principales. |
| :---- |

**08  /  MÉTODO CAIO · ETAPA 4**

**04\. TRADUCIR NEGOCIO A REQUERIMIENTOS**

Convertir una intención ambigua en algo entendible, validable y construible.

Aquí ocurre una de las transiciones más importantes del proyecto. Tenemos que transformar “Queremos automatizar esto” en especificaciones que eliminen ambigüedad.

| CHECKLIST DE CLARIDAD UN REQUERIMIENTO DEBE PERMITIR RESPONDER — Qué debe hacer el sistema. — Para quién. — Cuándo. — Con qué información. — Bajo qué reglas. — Conectado a qué sistemas. — Con qué nivel de calidad. — Bajo qué restricciones. — Cómo comprobaremos que funciona. |

**15  /  TRES GATES**

**CLAUDE NO DEBE DAR LUZ VERDE AUTOMÁTICAMENTE**

Antes de construir, la Skill PRD debe comprobar tres gates.

| VALOR GATE 01 · VALOR ¿Existe un problema suficientemente claro? Debemos conocer quién lo sufre, cómo ocurre, cuánto ocurre, qué impacto produce y qué resultado esperamos mejorar. Si no: detener y volver al diagnóstico. |
| :---- |

| VIABILIDAD GATE 02 · VIABILIDAD ¿Tenemos claridad suficiente sobre proceso, datos, sistemas, integraciones, restricciones, seguridad, personas y capacidad operativa? Si no: detener y resolver incertidumbres críticas. |
| :---- |

| VALIDACIÓN GATE 03 · VALIDACIÓN ¿Sabemos qué hipótesis queremos probar, cómo se medirá, qué resultado consideraremos satisfactorio y quién acepta el resultado? Si no: no construir todavía. |
| :---- |
